## 三、本轮发现并修复的问题

本轮测试的价值不仅是「跑通」，更在于暴露了三个此前未发现的前端缺陷。

### 问题 1：`audit_demo/app.js` 内容与 `index.html` 不匹配，导致仪表盘整页失效

**现象**：打开仪表盘，三卡片显示 `-`，环形图空白，最近记录「暂无扫描记录」。

**定位过程**：

1. 浏览器 Console 报错 `Cannot read properties of null (reading 'addEventListener')`
2. 读取 `audit_demo/app.js` 全文，发现其首行是 `$("scan-start-btn").addEventListener(...)`
3. 而 `scan-start-btn` 是 `scan.html` 的元素，`index.html` 中并不存在
4. 同时 `scan.html` 底部实际引用的是 `../js/pages/scan-page.js?v=2`，**并未引用 `app.js`**

**根因**：`audit_demo/app.js` 是早期单页版扫描逻辑的残留文件，被 `index.html` 引用后在第一行即抛出异常，后续渲染代码全部未执行。数据本身存在（扫描页历史有 10 条），只是仪表盘读不到。

**修复**：将 `audit_demo/app.js` 替换为仪表盘渲染实现（三卡片累计、环形图、最近 5 条记录）。原扫描页逻辑未受影响——它由 `js/pages/scan-page.js` 承担。

### 问题 2：报告页读到了过期数据（显示 `app.py` 11-19 的结果）

**现象**：完成 `sshd_bad.conf` 扫描后打开报告页，显示的是 `app.py`、扫描时间 `2026-11-19T14:41:28.220Z`、规则数 12——一条至少一天前的旧结果。

**定位过程**：

1. 报告页渲染器按固定 key 名依次尝试读取：`sap_local_reports` → `scanResult` → `lsap.lastScan`
2. 但项目内先后存在三套存储命名，且无一份契约文档统一说明：

| 写入方 | 键名 | 格式 |
|---|---|---|
| `js/api/local-reports.js`（经 `js/ui/storage.js`） | `sap_local_reports` | `过期时间|||json` 打包串，数组最新在前 |
| `audit_demo/app.js`（早期单页版） | `scanResult` | 裸 JSON 单条 |
| 早期方案文档 | `lsap.lastScan` | 实际无任何代码写入 |

3. 按固定顺序读取时命中了 `scanResult`（A 在 11-19 单页版扫描留下的一条），于是显示旧数据

**修复**：改为**遍历 localStorage 全部键**，凡具备扫描结果特征（含 `vul_list` / `scan_meta` / `stat`）的对象一律收集，去重后按时间戳（`created_at` 或 `scan_meta.scan_time`）倒序排列。报告页取第一条，仪表盘取全部做累计。

**修复收益**：

- 不再依赖任何固定键名，三套命名任一套写入即可读出
- 报告页永远显示**最新一次**扫描，不会停留在历史结果
- `token` / `user` / `api_base` 等无关存储项会被特征判断自动排除，不污染统计

**修复后验证**：报告页审计文件由 `app.py` 变为 `sshd_bad.conf`，扫描时间由 11-19 变为 11-20 23:41，明细由旧数据的 5 条变为本次的 3 条高危。

### 问题 3：统计数与明细数矛盾时的文案错误

**现象**（自测发现，非页面实测）：当 `stat` 记录有风险、但 `vul_list` 为空时，报告页顶部统计显示「高危 3」，明细区却写「本次扫描未发现问题，所有检查项通过」，自相矛盾。

**修复**：明细为空时区分两种情形——

- `stat` 合计为 0 → 「本次扫描未发现问题，所有检查项通过」
- `stat` 合计大于 0 → 「统计数据记录 N 项风险，但明细未随结果保存。请在审计任务页重新扫描该文件以生成完整报告」

避免答辩演示时出现「明明有漏洞却说没问题」的尴尬。

## 五、结论

**三角链路（扫描 → 仪表盘 → 报告页）本轮全部跑通。**

- 扫描侧：11 个用例结果全部符合期望，误报漏报为 0
- 仪表盘侧：累计统计与环形图自洽，最近记录排序正确
- 报告页侧：取数、渲染、排序、明细完整性均正确

但需注意：**上述「跑通」建立在本轮本地修复的 `app.js` 与 `report-app.js` 之上，两者尚未进入仓库。** 在修复文件上传之前，任何人从 `main` 拉取代码后打开仪表盘与报告页，看到的仍是占位与旧数据。

因此本轮的准确定位是：

> **功能已完成验证，交付尚未闭环。**

闭环条件为：`audit_demo/app.js`、`audit_demo/report-app.js`、`audit_demo/report.html`（一行脚本引入）三项改动进入 `main`，且 A 的仪表盘代码确认落到同一分支。
