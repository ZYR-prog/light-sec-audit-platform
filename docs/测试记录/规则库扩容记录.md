## 二、新增 6 条规则

| 编号 | 漏洞名称 | 级别 | 核心特征 | 设计要点 |
|---|---|---|---|---|
| VUL013 | SSH 协议版本 1 | 高危 | `Protocol 1` | 用 `\b1\b` 兼容 `Protocol 1,2`；`Protocol 2` 不命中 |
| VUL014 | 硬编码弱口令 | 高危 | `password = "123456"` | 只收 10 个典型弱口令 + **要求引号包裹**，避开日志中无引号的真实口令重复命中 |
| VUL015 | 命令执行 | 高危 | `os.system(` / `shell_exec(` / `subprocess(..., shell=True)` | 精确到 `shell=True` 分支，`subprocess.run([...])` 安全写法不误报 |
| VUL016 | 不安全反序列化 | 高危 | `pickle.loads(` / `yaml.load(` / `XMLDecoder` | `yaml.safe_load(` 与 `Loader=yaml.SafeLoader` 自动排除 |
| VUL017 | 异常详情输出 | 低危 | `traceback.print_exc()` / `printStackTrace(` | 与 VUL003（Debug 模式）互补，形成"信息泄露"组合 |
| VUL018 | 连接串明文口令 | 中危 | `mysql://user:pass@host/db` | `mysql://app@host/db`（无口令）不命中，零误报 |

**为什么选这 6 条**：覆盖「协议配置 → 凭据 → 执行 → 反序列化 → 信息泄露 → 连接串」6 类高频风险，且全部能用**单行正则**稳定匹配，符合本期纯前端、逐行扫描的技术边界。

## 四、扩容过程中修掉的一个真实误报

写 `weak_credential.py` 后发现多报 1 条中危：

```
第 15 行  VUL002  REAL_PASSWORD = os.getenv("APP_PASSWORD")
```

**原因**：VUL002 的正则 `password\s*[=:]\s*[^\s"']{3,}` 把 `PASSWORD = os.getenv(` 当成了"日志里打印明文密码"。

**修复**：在 VUL002 的 `exclude_pattern` 追加环境变量取值分支：

```
password\s*[=:]\s*(os\.(getenv|environ)|getenv|process\.env|system\.getenv)
```

**结果**：T10 从 3 条降为期望的 2 条，且 T04（demo_log.txt）不受影响，仍稳定命中 1 条。

> 这条记录值得在答辩时讲：**样例不是用来"证明我对"，而是用来"暴露我错"**——写完反例才发现原规则确实会误报。
