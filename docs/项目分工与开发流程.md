# 轻量级安全审计平台
## 项目分工与开发流程
## 一、项目概述
本项目为轻量级安全审计静态网站平台，采用"前端保底、后端加分"的渐进式开发策略：

• **保底方案**：纯前端静态网站，包含 Dashboard、审计任务、安全基线库、审计报告生成、帮助页五大模块，全部功能通过前端 JavaScript 实现，无需后端依赖。

• **加分方案**：在纯前端基础上增加 Flask 后端，提供用户系统、审计历史记录保存、报告存储回看等功能。后端采用"可插拔"设计，若未完成或接口不可用，前端自动降级为本地存储模式，不影响核心功能使用。

## 二、三人分工详情
- 2.1 成员 A — 页面 / 安全内容 / 融合对接负责人
核心定位： 页面搭建者 + 安全内容参与者 + 模块粘合剂。凭借 HTML 经验负责页面实现，同时作为网安方向学生参与安全内容设计，并承担各模块的融合对接工作。

|工作类别|具体内容|产出物|
|---|---|---|
|页面骨架开发|所有页面的 HTML + Tailwind 搭建，包括：• 顶部导航栏与侧边栏• Dashboard 仪表盘（统计卡片、饼图/柱状图画布、最近记录列表）• 审计任务页（上传区域、扫描按钮、进度条、结果表格）• 安全基线库（可折叠清单）• 审计报告页（报告结构与打印样式）• 关于/帮助页|可浏览的空壳页面集合（按钮点击无反应，但所有元素 id 预留完毕）  |

- 2.2 成员 B — 安全审计核心 / 扫描算法负责人
  
核心定位： 项目的安全大脑，负责漏洞体系设计与核心扫描算法实现，是安全审计功能的灵魂人物。

- 2.3 成员 C — 后端开发 / 通用前端 / 项目管理
  
核心定位： 后端的开发者 + 项目的大管家，横跨技术与管理两端。


平衡依据：

• B 技术难度最高，既要懂安全又要写核心扫描算法，但产出物数量适中
• A 工作面最广（页面 + 安全内容 + 融合对接），但凭借 HTML 经验和 AI 辅助效率较高
• C 总量最大（后端 + 通用 JS + 管理 + 文档），但安全零负担，走纯技术+管理路线

安全内容分工原则：

 A、B 均为网安方向，两人分摊安全内容。B 主攻漏洞体系与扫描算法（核心中的核心），A 负责基线库与报告模板（偏规范与文档类安全内容）。

## 四、开发流程（共 7 步）
### 第 1 步：需求与设计（全队协作，约 1 天）
目标： 统一认知，定好所有规范，避免后面返工。
具体工作：
1. 全队一起确认所有页面结构、功能点、按钮交互
2. 制定页面元素 id 命名规范、文件目录结构规范
3. B 输出漏洞规则初稿（列出漏洞种类、匹配思路）
4. C 输出后端接口清单初稿（列出需要哪些接口、入参出参）
5. A 输出页面草图（手绘或低保真线框图即可）
产出物：
• 页面草图 / 线框图
• id 命名清单
• 漏洞规则初稿
• 后端接口清单初稿
• 项目目录结构规范

### 第 2 步：并行开发 — 基础层（A、B、C 并行，约 3 天）
目标： 三人各干各的，把各自的基础工作做完。
成员 A — 页面骨架：
• 完成所有页面的 HTML + Tailwind 搭建
• 所有页面可浏览、布局正确
• 所有交互元素预留好 id
• 完成基础样式（颜色、字体、间距规范）
• 完成文件读取模块（FileReader 封装）
成员 B — 漏洞库与规则：
• 完成漏洞库设计（至少 15 条漏洞，覆盖高/中/低危）
• 完成匹配规则文档（每条漏洞的检测关键词/正则说明）
• 完成测试样例初稿
成员 C — 后端雏形：
• 搭建 Flask 项目骨架
• 设计并创建 SQLite 数据库表（用户表、审计记录表、报告表）
• 完成基础接口：/api/ping、注册、登录
• 搭建 Git 仓库，初始化项目结构
产出物：
• A：可浏览的空壳前端 + `fileReader.js`
• B：`vulnerabilities.json` + `scan-rules.md` + 测试样例初稿
• C：Flask 后端雏形 + GitHub 仓库

### 第 3 步：并行开发 — JS 逻辑层（B + C 各写各的 JS，约 3 天）
目标： 把所有 JavaScript 逻辑写完，各自独立测试通过。
成员 B — 核心扫描 JS：
• 基于 A 的文件读取模块，编写关键词匹配扫描逻辑
• 编写正则匹配扫描逻辑
• 实现漏洞判定与等级分类
• 实现漏洞数据组装（位置标记、统计汇总）
• 用测试样例独立调试扫描功能
• 输出扫描结果数据结构规范
成员 C — 通用交互 JS：
• 弹窗组件（成功 / 警告 / 确认）
• 表格筛选与排序函数
• 折叠面板 / 标签页切换
• localStorage 存储封装（存进度、存历史）
• 通用工具函数库
• 审计报告前端渲染（数据结构按 B 的规范）
成员 A — 并行完善安全内容与准备对接：
• 完成安全基线库内容（等保 2.0、Linux 基线、Web 配置基线）
• 完成审计报告内容模板设计
• 熟悉 B 的扫描模块和 C 的通用模块接口
• 准备融合对接的页面结构
产出物：
• B：`scan.js`（独立可运行，能用测试样例扫出漏洞）+ 数据规范
• C：`ui.js` + `utils.js` + `report.js`（各自独立可用）
• A：`baseline.json` + `report-template.md`

### 第 4 步：融合对接（A 主力，C 配合，约 2 天）
目标： 纯前端版本完整跑通，达到保底交付标准。
关键里程碑：此步完成 = 保底版本完成，后面的后端做不成都能交作业。
具体工作：
6. A 把所有 JS 模块嵌入对应 HTML 页面底部
7. A 通过 id 绑定，打通全流程：上传文件 → 读取内容 → 开始扫描 → 进度条动画 → 结果表格渲染 → 图表渲染；基线库折叠交互；生成报告 → 报告页面渲染 → 打印/导出 PDF
8. C 配合把通用组件（弹窗、筛选等）接到对应页面
9. B 进行第一轮功能测试：用测试样例测扫描准确性；反馈误报、漏报问题；检查漏洞描述、修复建议是否正确
10. A 根据 B 的反馈调整扫描规则
产出物：
• 完整可运行的纯前端版本（保底交付版）
• 第一轮测试反馈记录

### 第 5 步：后端接入（C 主力，A 配合，约 2-3 天，可选）
目标： 把后端接进来，实现用户系统与历史记录功能。此步为加分项，未完成不影响提交。
具体工作：
11. C 完善后端接口：审计历史记录 CRUD 接口；报告保存与读取接口；接口权限校验（登录态检查）
12. C + A 一起写前端对接代码：登录 / 注册页面交互；扫描完成后自动保存历史记录；Dashboard 从后端加载统计数据和最近记录；历史记录列表页与详情页
13. C 实现降级逻辑：所有后端调用封装统一错误处理；接口失败或超时时自动切换为 localStorage 模式；确保后端挂了前端照样能用
14. B 同步继续完善安全内容和测试样例
产出物：
• 带后端的完整版本（加分项）
• 后端降级机制验证通过

### 第 6 步：美化 + 调 bug + 补内容（约 2 天）
目标： 打磨细节，修复问题，扩充内容。
成员 A：
• 样式微调（间距、颜色、动画优化）
• 响应式适配（不同屏幕尺寸）
• 修前端 bug
• 性能优化
成员 B：
• 补充漏洞描述和修复建议的详细程度
• 扩充基线库内容
• 增加更多测试样例
• 进行第二轮完整测试
成员 C：
• 修后端 bug
• 完善通用交互组件细节
• 整理测试记录
• 开始准备 README 框架
产出物：
• 最终版产品（纯前端版 / 带后端版）
• 完整测试记录

### 第 7 步：文档 + Git + 部署 + 打包（C 牵头，约 1 天）
目标： 完成所有交付物，准备提交。
具体工作：
15. A 撰写前端模块功能介绍文字
16. B 撰写安全审计模块功能介绍文字
17. C 整合润色，完成 README.md 全部内容：设计理念、项目简介、使用方法、难点与解决方案、项目结构说明
18. C 整理代码，提交到 GitHub 主分支
19. C 部署 GitHub Pages（纯前端版）
20. C 打包提交文件：项目源代码（压缩包）、项目可执行文件 / 部署说明、README.md
21. 全队最终检查一遍
产出物：
• README.md
• GitHub 仓库（含完整提交历史）
• GitHub Pages 在线访问地址
• 提交文件包（源代码 + 可执行文件 + 文档）

## 五、关键设计原则
1. 保底优先原则

永远保证纯前端版本可用。后端是加分项，任何时候后端做不下去，把前端切到"纯本地模式"就能交作业。

2. 并行开发原则

能并行的工作尽量并行，减少等待。第 2 步和第 3 步是主要的并行阶段，三人同时开工。

3. 接口先行原则

前端和后端通过接口定义对接。第 1 步就把接口清单定好，两边各做各的，最后联调。

4. 渐进式增强原则

功能按"核心 → 重要 → 锦上添花"的顺序开发。先保证能跑，再做好看，再加后端增强。

5.  文档同步原则
6.  
C 全程跟进文档和过程记录，不要等最后才补。需求变更、问题解决、测试结果都要及时记录。
