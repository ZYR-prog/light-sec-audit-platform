## 一、这份规范解决什么问题

项目里扫描结果要被三处消费：**页面表格（A）、详情弹窗（A）、报告页与数据库（C）**。如果三个人各自猜字段名，就会出现“后端存进去了、前端读不出来”的经典联调事故。

本项目实际发生过：第一轮联调时 `scan.html` 状态栏显示 5 条，但表格是空的——原因是渲染端去读 `result.list`，而扫描端产出的是 `result.vul_list`。**一个字段名对不上，整块功能哑火。**

所以这份规范定义三件事：

1. **结构长什么样**（三层：`vul_list` / `stat` / `scan_meta`）
2. **每个字段叫什么、什么类型、什么约束**
3. **怎么校验它是对的**（`validateResult()`）

**总约束一条**：扫描端唯一出口是 `js/core/scan.js` 的 `scanText()`，任何人不许自己拼一个“差不多”的对象。

## 二、三层结构总览

`scanText()` 返回一个对象，固定包含三个键：

```javascript
{
  vul_list: [...],   // 漏洞明细数组，无命中时为 []
  stat: {...},       // 分项统计
  scan_meta: {...}   // 本次扫描的元信息
}
```

| 键 | 类型 | 用途 |
|---|---|---|
| `vul_list` | 数组 | 表格每一行、详情弹窗、报告明细、数据库存的主要载荷 |
| `stat` | 对象 | 顶部统计卡片、仪表盘三卡片、图表数据源 |
| `scan_meta` | 对象 | 报告头信息、性能核对、异常诊断 |

三者的关系：`stat.total` 必须等于 `vul_list.length`（由 `validateResult()` 强制校验）。

---

## 三、vul_list 漏洞明细

数组中每个元素是一条漏洞记录，**固定 8 个字段，顺序即前端展示顺序**。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `vid` | string | 形如 `VUL001` | 规则编号，可据此到 `vulnerabilities.json` 查完整规则 |
| `vname` | string | 非空 | 漏洞名称，直接用规则库里的 `vname` |
| `level` | string | **只能是 `高危` / `中危` / `低危`** | 中文三值，不接受 `high` / `mid` / `low` |
| `line` | number | **整数，从 1 开始** | 命中行号，文件第一行 = 1 |
| `hit_content` | string | **已 trim，最长 200 字** | 命中的那一行原文（超长由扫描端截断，渲染端不用再截） |
| `description` | string | 非空 | 漏洞原理说明（为什么危险） |
| `suggestion` | string | 非空 | 修复建议（改哪一行、改成什么） |
| `file_name` | string | 可为空 | 所属文件名；单文件接口下等于 `scan_meta.file_name` |

**字段产出的唯一出口**是 `createVulRecord(rule, line, hitContent, fileName)`：

```javascript
import { createVulRecord } from "./data-schema.js";

const item = createVulRecord(rule, 9, "PasswordAuthentication yes", "sshd_bad.conf");
```

该函数内部完成两件事，所以调用方**不要自己再处理**：

```javascript
hit_content: String(hitContent ?? "").trim().slice(0, 200)
```

## 四、stat 统计对象

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `high` | number | ≥ 0 | 高危条数 |
| `mid` | number | ≥ 0 | 中危条数 |
| `low` | number | ≥ 0 | 低危条数 |
| `total` | number | = high + mid + low | 总条数 |

**必须满足**：`stat.high + stat.mid + stat.low === stat.total`。`validateResult()` 会检查这一条，不满足直接报错。

**为什么不用 `vul_list.length` 代替 `total`**：两者数值应相等，但 `stat` 是**独立可传递的摘要**——历史记录列表、仪表盘卡片只需要统计数字，不必传整个 `vul_list`。`lsap.history` 里存的就是摘要。

空结果用 `emptyStat()` 生成：`{ high: 0, mid: 0, low: 0, total: 0 }`。

## 五、scan_meta 扫描元信息

**六个字段必须全部存在**（`validateResult()` 逐个检查 `in` 运算符）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `file_name` | string | 被扫描文件名（含扩展名） |
| `total_lines` | number | 文件总行数，空文件为 0 |
| `rule_count` | number | 本次参与匹配的规则条数（当前规则库为 **18**） |
| `rule_error_count` | number | 正则编译失败被跳过的规则条数，正常为 **0** |
| `cost_ms` | number | 扫描耗时（毫秒） |
| `scan_time` | string | 扫描时间，**ISO 8601 字符串**，供后端落库与报告头展示 |

### rule_error_count 的意义

`> 0` 表示规则库里有正则写错了（括号不配、转义不全），该条被跳过、其余规则照常执行。

**这个字段是“如实反映降级”的开关**：

- 前端可据此提示「18 条规则中 1 条加载失败」
- 报告开头展示「规则异常：1 条加载失败」
- 测试时它是回归信号——正常应恒为 0，非 0 说明规则库有维护事故

**不要把它当无关字段忽略。**

## 六、风险等级枚举与视觉映射

代码中通过 `LEVEL` 常量使用，避免手写中文字符串拼错：

```javascript
import { LEVEL, LEVEL_LIST, LEVEL_CLASS, LEVEL_COLOR } from "./data-schema.js";

LEVEL.HIGH // "高危"
LEVEL.MID  // "中危"
LEVEL.LOW  // "低危"
LEVEL_LIST // ["高危", "中危", "低危"]  ← 固定展示顺序
```

配套的两套视觉映射，**前端直接用，不要自己另配颜色**：

| 等级 | 徽章 CSS 类（`LEVEL_CLASS`） | 图表颜色（`LEVEL_COLOR`） |
|---|---|---|
| 高危 | `risk-high` | `#ef4444`（红） |
| 中危 | `risk-mid` | `#f59e0b`（橙黄） |
| 低危 | `risk-low` | `#3b82f6`（蓝） |

`scan.html` 的 `<style>` 里已经定义了 `.risk-high / .risk-mid / .risk-low` 三个类（半透明背景 + 对应文字色），报告页也同样可用。

**注意：本规范没有“无风险”等级。**
扫描结果为 0 条时不产生任何记录，由页面显示空状态（“未检出风险项”）。阴性样例（干净代码、正常日志、注释配置、空文件）验证的就是这种情形。

## 八、三个最容易踩的坑

### 坑 1：字段名是 `vul_list`，不是 `list`

```
❌ result.list          → undefined，表格渲染成空
✅ result.vul_list
```

这是**真实发生过的联调事故**：第一轮 A 的页面状态栏显示“检出 5 条”，表格却一行没有——数据在，读的键名错了。

### 坑 2：`level` 是中文三值，不是英文

```
❌ "high" / "mid" / "low" / "High" / "高"
✅ "高危" / "中危" / "低危"
```

`validateResult()` 会用 `LEVEL_LIST.includes(v.level)` 校验，英文值直接判为非法。

**为什么定中文**：徽章文字、报告文字、统计标签全用中文，避免在渲染端反复做 `high → 高危` 的映射（映射表最容易漏一个分支，导致徽章变成默认色）。

**后端落库时也不要转**。`backend/routes/reports.py` 是原样存 `vul_list`，前端读回来直接用。若某天需要英文枚举（例如对接外部系统），应在独立字段里增加，**不要动 `level`**。

### 坑 3：`hit_content` 已截断，渲染端不要二次截断

```
扫描端：String(hitContent).trim().slice(0, 200)   ← 已处理
渲染端：直接显示，不要再 slice
```

但**表格列需要截短**（页面表格里只显示 50 字）是另一回事——那是**展示层截断**（`truncate(item.description, 50)`），用的是 `description` 而非 `hit_content`，两者不要混。

| 字段 | 存的内容 | 表格列显示 | 详情弹窗显示 |
|---|---|---|---|
| `description` | 完整说明 | 截 50 字 + 省略号 | 完整 |
| `hit_content` | 原行已有 200 字上限 | 不显示 | 完整（≤200 字） |

## 九、校验函数用法

`validateResult(result)` 返回**错误描述数组**，空数组表示完全合规。

```javascript
import { validateResult } from "./data-schema.js";

const errors = validateResult(result);
if (errors.length) {
  console.error("扫描结果不符合契约：", errors);
  // 开发期直接抛错，避免脏数据流到下游
}
```

### 它具体检查哪些规则

| 检查项 | 违规时的错误信息 |
|---|---|
| 结果是否为对象 | `结果不是对象` |
| `vul_list` 是否为数组 | `vul_list 必须是数组` |
| `stat` 是否存在 | `缺少 stat 对象` |
| `stat` 四个字段是否都是数字 | `stat.high 必须是数字`（逐个报） |
| **分项之和是否等于 total** | `stat 分项之和不等于 total` |
| `scan_meta` 是否存在 | `缺少 scan_meta 对象` |
| `scan_meta` 六字段是否齐全 | `scan_meta 缺少字段 cost_ms`（逐个报） |
| 每条记录 8 字段是否齐全 | `vul_list[0] 缺少字段 file_name` |
| `level` 是否合法 | `vul_list[0] 等级非法：high` |
| `line` 是否为 ≥1 的整数 | `vul_list[0] 行号非法：0` |

### 建议在哪调用

| 场景 | 是否调用 |
|---|---|
| `selftest.mjs` 每个用例结束后 | **必须**（这是回归护栏） |
| 页面扫描完成后（开发期） | 建议，`console.error` 即可 |
| 生产/演示环境 | 不必，避免影响速度 |

## 十、下游消费约定

### A｜页面表格（`js/pages/scan-page.js`）

| 列 | 取字段 | 处理 |
|---|---|---|
| # | 数组下标 + 1 | — |
| 漏洞名称 | `vname` | 直接显示 |
| 风险等级 | `level` | 徽章，class 用 `LEVEL_CLASS[level]` |
| 位置 | `line` | 拼成「第 X 行」 |
| 描述 | `description` | `truncate(…, 50)` 截断 |
| 操作 | — | 「详情」按钮 → 打开弹窗 |

### A｜详情弹窗

标题取 `vname`，副标题拼 `vid · level · 第 X 行`，正文四段：`file_name` / `hit_content` / `description` / `suggestion`。

### A/C｜报告页

| 区块 | 取字段 |
|---|---|
| 报告头 | `scan_meta` 全六项 |
| 风险总览 | `stat` 四项 |
| 漏洞明细 | `vul_list` 按 `level`（高→中→低）、同级按 `line` 升序排列 |
| 页脚 | `stat.total` 与 `stat.high` |

### C｜后端落库

`POST /api/reports/save` 时**原样提交** `{ vul_list, stat, scan_meta }` 三个键，不做字段重命名、不做等级转换。

`report_type` 只接受 `file` / `url` 两个值。
