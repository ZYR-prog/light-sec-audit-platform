## 一、模块定位

安全审计模块是平台的**检测引擎**：用户上传一份配置文件、日志或代码片段，模块在浏览器内完成逐行特征匹配，找出其中的安全缺陷，并给出风险等级、命中位置、漏洞原理与修复建议。

它是整个平台唯一「产生安全结论」的模块，其余部分（页面、图表、历史记录）都围绕它的输出展开。

**一句话概括**：
> 规则库定义"什么是漏洞"，扫描算法负责"在文件里找出它们"，数据结构规范保证"整条链路说的是同一种话"。

## 二、三项核心能力

### 2.1 可扩展的漏洞规则库

规则库以纯 JSON 描述，一条规则 = 一个漏洞类型：

| 字段 | 作用 |
|---|---|
| `vid` | 规则编号（VUL001…），结果里唯一可追溯的标识 |
| `vname` | 漏洞名称，直接展示给用户 |
| `level` | 风险等级（高危 / 中危 / 低危） |
| `pattern` | 命中漏洞特征的正则 |
| `exclude_pattern` | **排除正则**，用来过滤误报 |
| `description` | 漏洞原理说明 |
| `suggestion` | 修复建议 |

当前内置 **12 条规则**，覆盖三类对象：

| 类别 | 规则示例 |
|---|---|
| SSH / 系统配置 | 开启密码登录、允许 root 远程登录、允许空口令 |
| Web 服务配置 | Debug 模式开启、目录浏览、SSL 关闭、TRACE 开启 |
| 日志与源代码 | 日志明文密码、硬编码密钥、`eval` 动态执行、SQL 字符串拼接、MD5 弱哈希 |

**规则可扩展**：新增一类漏洞只需往 JSON 里加一条，**不改任何一行算法代码**。维护流程写在 `data/scan-rules.md`。

### 2.2 带「双重校验」的扫描算法

核心逻辑是三层循环：`规则 × 行`，但每次命中都要过两道闸：

```
第一道闸：命中 exclude_pattern → 判定为误报，跳过
          （过滤注释行 # // ; --、已脱敏的 ***、[masked]、示例占位值）
第二道闸：命中 pattern → 确认漏洞，记录行号与命中原文
```

**为什么必须有排除规则**：安全审计里最怕的不是漏报，而是**误报**。一份配置里被注释掉的三行高危配置，如果不排除，用户会看到 3 条"高危"，从此不再信任这个工具。

实测数据：`sshd_comment.conf`（三行高危特征全部写在注释里）扫描结果为 **0 条**，`sshd_good.conf`（配置全部达标）同样 **0 条**。

### 2.3 全队统一的数据结构规范

扫描结果由 `js/core/data-schema.js` 统一生产，包含三部分：

| 部分 | 内容 | 使用者 |
|---|---|---|
| `vul_list` | 漏洞明细数组（8 个字段） | 页面表格、详情弹窗、报告 |
| `stat` | 分项统计 `{high, mid, low, total}` | 仪表盘三张卡片、饼图 |
| `scan_meta` | 扫描元信息（文件名、行数、规则数、耗时、扫描时间） | 操作留痕、历史记录入库 |

同时提供 `validateResult()` 用于联调期自检：字段缺失、等级取值非法、分项之和不等于总数，都会立刻报出来。

## 三、技术实现要点

| 要点 | 做法 | 解决什么问题 |
|---|---|---|
| **纯前端执行** | 文件只在浏览器内存中处理，不上传服务器 | 敏感日志/配置不出本地，符合安全要求 |
| **规则库路径自定位** | `new URL("../../data/vulnerabilities.json", import.meta.url)` | 页面放在任何子目录都不会 404 |
| **规则库按需缓存** | `getRules()` 首次加载后缓存 | 连续多次扫描不重复请求 |
| **单条规则容错** | 每条规则的正则编译单独 try/catch | 一条写错不会让整个扫描崩溃，同时通过 `rule_error_count` 暴露出来 |
| **去除 g / y 标志** | 编译时统一 `replace(/[gy]/g,"")` | 避免 `test()` 的 `lastIndex` 漂移造成偶发漏报 |
| **换行符归一化** | `\r\n` / `\r` 统一转 `\n` | Windows 文件行号不错位 |
| **纯函数设计** | 不碰 DOM、不读文件、不依赖页面 | 可在命令行直接跑回归测试 |
| **事件解耦** | 扫描完成只广播 `scan:complete` 事件 | 页面渲染与数据入库互不依赖 |

## 四、在平台中的位置与数据流

```
用户选择文件
      ↓
  file-reader.js（队友A）  → 读出文件文本
      ↓
  scan.js（队友B）         → 规则库加载 → 逐行匹配 → 输出结果
      ↓
  audit-task.js（队友A）   → 填充 6 列结果表、更新进度与状态
      ↓
  scan:complete 事件
      ├─→ dashboard.js（A）→ 更新三张卡片与风险分布图
      └─→ history.js（C）  → 扫描记录入库、写操作留痕
```

## 五、质量保证

**自动化回归**：`node test-samples/selftest.mjs`

7 份样例覆盖 4 类文件、7 个测试维度（含注释误报、脱敏误报、正常文件零误报），当前 **7/7 通过**。每次修改规则库或算法都必须重跑，防止"规则写错导致静默失效"。

**开发过程中真实修掉的 3 个缺陷**：

| 缺陷 | 表现 | 根因 |
|---|---|---|
| VUL006 规则静默失效 | 硬编码密钥一条都扫不出，且无报错 | 排除正则里写了 `***`，构成非法正则 |
| 规则库 404 | 页面移动后加载失败 | `fetch` 相对路径以页面为基准 |
| 偶发漏报 | 同一文件两次扫描结果不同 | 正则带 `g` 标志导致 `lastIndex` 漂移 |

> 这三条都写进了 `docs/测试记录.md`，是"为什么必须有回归测试"的最好例证。

## 六、已知局限

| 局限 | 说明 |
|---|---|
| 只做正则特征匹配 | 不做语义分析，变形/混淆写法可能漏报 |
| 逐行匹配，不跨行 | 特征被拆到两行的配置识别不到 |
| 单文件扫描 | 不跨文件关联（如配置引用的证书文件） |
| 规则库 12 条 | 覆盖面有限，可继续扩展 |
| 编码假设 UTF-8 | GBK 文件中文匹配可能异常 |
| 未做大文件压测 | 1MB 以上文件性能未验证 |

## 七、一句话总结（可直接放 README 首段）

> **安全审计模块**采用"可扩展规则库 + 双闸匹配算法 + 统一数据契约"的设计，在浏览器本地完成配置文件、日志与代码的安全缺陷检测，输出带风险等级、精确行号、原理说明与修复建议的结构化结果，整体无需服务端参与即可独立运行，并通过 7 份样例的自动化回归保证准确性与零误报。
