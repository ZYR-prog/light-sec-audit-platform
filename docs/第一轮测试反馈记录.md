## 四、发现的问题与反馈（按优先级）

### 🔴 P1：描述列最终采用 `hit_content`，需注意长文本

**现状**：A 的页面在「描述」列显示 `hit_content`（命中的那行原文），例如 `API_KEY = "vFZX..."`、`eval(...)`、`SELECT ... FROM ...`、`md5(...)`。

**评价**：
- 优点：用户能直接看到"哪一行、什么内容"出了问题，定位直观。
- 风险：长密钥、长 SQL 语句会撑破行高，破坏表格对齐（已在 T07 中出现类似长串）。

**建议**：
- 保留 `hit_content` 作为表格「描述」列（可视化更好）；
- 但**必须配合 P2 的两行截断**，超出部分在详情弹窗里完整查看。

> 备选方案：表格显示 `description`（原理说明），弹窗显示 `hit_content`。两种都可，B 侧字段都已提供，A 只需换一个字段名。

---

### 🟡 P2：长文本会把表格撑变形（本轮确认存在）

T07（`app.py`）与 T06 中，命中的密钥、SQL、哈希值长度超过 40 字符，表格行高明显增高。

**建议在 `css/components.css` 增加**：

```css
#result-table-body td:nth-child(5) {
  max-width: 320px;
  overflow: hidden;
  text-overflow: ellipsis;
  display: -webkit-box;
  -webkit-line-clamp: 2;      /* 最多两行 */
  -webkit-box-orient: vertical;
  word-break: break-all;      /* 长串强制换行，避免撑破 */
}
```

---

### 🟡 P3：进度条动画需确认（体验问题）

扫描耗时仅 1~3ms，用户点完文件后进度条可能瞬间跳到 100%，看起来像"没反应就结束了"。

**建议 A 在 `audit-task.js` 中加入最小展示时长**：

```js
const MIN_MS = 400;
const t0 = performance.now();
const result = await scanText(text, file.name);
const rest = MIN_MS - (performance.now() - t0);
if (rest > 0) await new Promise(r => setTimeout(r, rest));
```

**说明**：进度条是反馈机制，扫描瞬时完成时给用户可感知的过程属于正常交互设计，答辩可主动说明。

---

### 🟡 P4：详情按钮与弹窗组件对齐

B 侧已做三级降级：`window.openModal(html)` → 自填 `#modal-container` → `alert`。

**需要 A 确认**：若 C 的 `js/ui/modal.js` 可用，只需挂一行：

```js
import { openModal } from "../ui/modal.js";
window.openModal = openModal;   // B 的详情按钮会自动走统一组件
```

### 🟢 P6：扫描结果跨页面传递（A 提出，方案已定）

**问题**：扫描结果需在「审计报告」页展示，需持久化。

**结论：采用 localStorage（方案 a）**，约定如下：

| key | 内容 |
|---|---|
| `lsap.lastScan` | 最近一次完整 `result` 对象（JSON.stringify） |
| `lsap.history` | 历史记录数组，仅保留最近 10 条 |

写入时机：`scanText()` 返回后，与 `renderTable()`、`updateCards()` 同一处调用 `saveScanResult(result)`。
报告页读取 `lsap.lastScan` 后渲染，无数据时显示「暂无扫描结果」。**注意**：
- localStorage 按域名隔离，本地 `localhost:8000` 与将来 GitHub Pages 域名不互通（演示在本地不受影响）；
- 结果内含文件原文片段，正式版应改为后端加密存储（答辩可主动说明为演示版简化）。

## 五、已知的漏报风险（诚实说明，答辩可主动提）

| 场景 | 漏报原因 | 是否补 |
|---|---|---|
| 配置写成 `PasswordAuthentication=yes`（等号分隔） | 规则按空白分隔匹配 | 可扩展 `\s*[=\s]\s*` 兼容 |
| 漏洞特征跨两行（如 `PermitRootLogin` 与 `yes` 分行） | 逐行匹配，不跨行 | 不补（成本高收益低） |
| GBK 编码的中文文件 | 按 UTF-8 读取，中文可能乱码 | 第二轮补测 |
| 变形/混淆写法（如 `P a s s w o r d`） | 正则特征匹配的固有限制 | 不补，在 README「已知局限」说明 |

> 已写入 `docs/scan-core-README.md` 第八节，答辩主动说明优于被问出。
